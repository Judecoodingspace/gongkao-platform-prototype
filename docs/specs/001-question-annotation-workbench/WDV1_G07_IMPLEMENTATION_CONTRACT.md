# WDV1-002 / G-07 原始 DOCX 接收实施合同

**状态：APPROVED（实施授权）。** 本文把已通过的 G-06 产品决定收敛为 WDV1-002 的可验收边界。它授权原始 DOCX 的安全接收和来源版本定稿；它不授权解析器、预览、React 页面、生产存储桶选择或 G-08/G-09 工作，也不表示 G-07 已通过。

**上位依据：** [`WDV1_G06_FROZEN_DECISIONS.md`](./WDV1_G06_FROZEN_DECISIONS.md)、[`word-assisted-annotation-v1.md`](./word-assisted-annotation-v1.md)、[`data-model.md`](./data-model.md) 与现有 Shenlun API 合同。若发生冲突，以 G-06 冻结决定和既有不可变版本规则为准，并暂停实施以补充评审。

## 1. 目标与完成物

WDV1-002 只交付一件事：受控操作者能够把一个经安全检查的 DOCX 作为一个可追溯、不可替换的来源版本接收进系统。

一次成功接收必须得到：

- 一个明确归属的 `Paper`；以及其首个或后续的 `PaperVersion`；
- 私有存储中完整、原样的文件体；
- 原始显示文件名、固定文件类型 `docx`、SHA-256、私有存储引用、创建者、创建时间和 `finalized` 状态；
- 不泄露私有存储路径或文件内容的操作结果与审计记录。

`PaperVersion` 是来源证据，不是解析任务、题目草稿或材料。接收成功后，文件与元数据不可被上传、解析或录题操作覆盖；内容改变时只能产生新的版本。

## 2. 明确范围

### 本合同内

1. 接收一个新来源试卷，或向已存在的 `Paper` 添加一个新的来源版本。
2. 在服务端完成 DOCX 格式和安全边界验证、计算 SHA-256、私有持久化和来源版本定稿。
3. 为上传重试提供幂等保证；为可恢复的基础设施失败提供安全错误结果。
4. 用脱敏 DOCX fixture、PostgreSQL 16 和私有测试存储验证 G-07。

### 本合同外

- 文字、图片、表格、公式、页码或坐标的解析；`DocumentBlock`、`SourceSpan`、解析任务或处理历史；
- 视觉预览、下载原件、来源块选择、字段填入、题目创建/提交或审核；
- PDF、`.doc`、`.docm`、扫描件、OCR、宏、嵌入活动内容和图文题字段；
- 正式登录、RBAC、对象存储供应商选择、归档/销毁策略和 React 上传工作台。

因此，G-07 不得以“可解析”“可预览”或“可自动拆题”作为通过条件。它只证明原始 DOCX 已安全、完整且可追溯地进入系统。

## 3. 既有模型的使用方式

不重建 `papers` 或 `paper_versions`，也不改变其不可级联删除约束。现有 M-001 已提供以下最小字段：`file_name`、`file_type`、`file_hash`、`storage_uri`、`upload_status`、`created_at`、`created_by`，以及同一 `paper_id` 下唯一的 `version_number`。

G-07 对这些字段的固定解释如下：

| 字段 | G-07 合同含义 |
| --- | --- |
| `file_name` | 去除目录和控制字符后的原始显示文件名；不是存储路径，也不从文档正文推断题名。 |
| `file_type` | 固定为 `docx`，避免把超出既有字段长度的 MIME 字符串伪装成数据模型。 |
| `file_hash` | 成功持久化字节的 SHA-256 小写十六进制值。 |
| `storage_uri` | 不可猜测的私有存储引用；不得是公开 URL，也不得在普通 API 响应、前端日志或错误信息中返回。 |
| `upload_status` | 对 G-07 已成功接收的版本一律为 `finalized`。`uploaded` 不作为对外成功结果；`failed` 不得被用于伪造一个并未完整保存的来源版本。 |
| `parser_*` | G-07 一律为空；填入任何解析器名称、版本或配置属于 G-08 之后的工作。 |

被请求拒绝或因存储失败而没有完整持久化的文件，不创建 `PaperVersion`。可记录仅含操作者 ID、请求 ID、错误代码、大小类别和时间的安全审计事件；不得保存文件正文、完整私有路径或失败文件的哈希冒充已接收来源。

## 4. 接收语义

### 4.1 两种明确意图

实现必须区分下列用户明确选择的意图，不能由文件名或 DOCX 正文推断：

| 意图 | 必填业务信息 | 成功结果 |
| --- | --- | --- |
| 新建来源试卷 | `title`、`subject`、`exam_type`；`province`、`year` 可选 | 创建一个 `Paper` 和版本号 `1` 的 `PaperVersion`。 |
| 上传新来源版本 | 已存在的 `paper_id` | 在该 `Paper` 下以互斥方式分配下一个版本号并创建新 `PaperVersion`。 |

元数据由受控操作者明确提供；系统不得从文件名、页眉、正文或解析器猜测省份、年份、学科、考试类型或题名。若上传的是新版本，原 `Paper` 和所有旧 `PaperVersion` 均保持不变。

### 4.2 成功的原子性边界

成功响应只能在以下条件全部成立后返回：文件完成安全验证、完整字节写入私有存储、服务器以实际写入字节计算 SHA-256、并且 `Paper`（如适用）、`PaperVersion` 与安全审计事件已提交。

持久化过程使用不公开的暂存位置。数据库提交失败时，暂存件可以清理；若底层存储已不可逆地写入但数据库未提交，系统不得把该文件当作已接收来源，也不得返回成功。它必须留下不含内容的运维告警/可清理记录，由受控人员处理孤立件。任何恢复动作都不得删除已经 `finalized` 的版本。

### 4.3 重试与重复内容

- 写请求必须带客户端生成的 `client_request_id`，沿用既有 `(actor_id, operation_scope, client_request_id)` 幂等语义。
- 同一键、相同载荷和同一文件字节重放，返回同一来源版本，不创建第二条记录；同一键而元数据或文件字节不同，返回 `409 IDEMPOTENCY_CONFLICT`。
- 对同一个 `Paper`，不同幂等键再次上传相同 SHA-256 的文件，**不得创建新的 `PaperVersion`**。API 合同可在实施时选择返回既有版本、返回明确的 duplicate result，或返回 `409`；它必须在 API 合同和测试中固定一种可重放、可理解的语义，且不得把重复内容伪装成新的来源版本。
- 不同 `Paper` 之间不以哈希做全局去重或合并，避免把两个人工确认的来源身份误判为同一试卷。

## 5. DOCX 安全与输入规则

接收端同时满足以下条件才可视为“安全、有效的 DOCX”：

1. 文件扩展名为 `.docx`，客户端声明的类型只能作为提示，不能替代服务端检查。
2. 文件大小、ZIP 条目数、解压后总大小和单条目压缩比必须受限；任何超限包在解压、渲染或解析前拒绝。
3. 文件是可读取的 Office Open XML ZIP 包，含 Word 主文档和必需的内容类型声明。
4. 包中不得含宏、ActiveX、OLE/嵌入包或可导致远程资源访问的外部嵌入；具体关系类型规则见下文。`.docm` 及任何检测到 `vbaProject`、ActiveX 或 OLE/嵌入对象的包一律拒绝。
5. 验证过程只检查容器结构、关系类型和安全属性；不得执行宏、打开、下载或跟随任何外部资源，不得渲染文档、提取正文、调用 OCR 或赋予业务语义。

普通 DOCX 中的图片、表格、公式图片、分页和长文本不是拒绝理由。G-07 只原样保留它们，不保证本阶段可以显示或理解它们。

### 5.1 OOXML relationships 的区别处理

DOCX 的关系记录位于包内的 `.rels` 文件。G-07 必须检查这些记录的**类型**和 `TargetMode`，但绝不访问其中的目标。

| OOXML 情形 | G-07 处理 | 原因 |
| --- | --- | --- |
| `…/relationships/hyperlink` 且 `TargetMode="External"` 的普通 Word 超链接 | 接收；原样保存；不解析、不预取、不检测链接是否可访问，也不在本阶段显示为可点击内容。 | 超链接只是文档文字的引用，单独存在不应使正常 DOCX 失效。 |
| 非 hyperlink 的 `TargetMode="External"`，例如外链图片、外链模板、外链 `altChunk`、外链 OLE/包或其他可请求远程资源的关系 | 拒绝该文件。 | 后续预览或处理可能触发远程读取；G-07 不以“当前尚未访问”来保留该风险。 |
| 宏、ActiveX、OLE/嵌入包、控件或等价活动内容，例如 `vbaProject.bin`、`word/activeX/`、`word/embeddings/`、OLE/控制关系 | 拒绝该文件。 | 不可信上传件不得携带可执行或可激活对象进入来源库。 |

实现不得仅用扩展名、MIME 类型或字符串搜索代替 OOXML 包关系检查。验收必须包含一个带普通外部超链接的脱敏 DOCX，它应被接收且验证过程无网络访问；还必须包含外链图片/模板/`altChunk` 之一和活动内容代表样本，它们应被拒绝且不产生 `PaperVersion`。

### 5.2 `IMPLEMENTATION_PRECHECK`：阈值建议，不是产品批准数字

产品负责人已批准“必须有文件和压缩包安全限制”，但没有批准具体数字。在本次合同修订中，对本地、Git 忽略的 3 个 DOCX POC 样本只读取 ZIP 元数据（未解压、未读取正文、未输出文件名），得到：最大原文件 **594,257 B（约 0.57 MiB）**、最大解压内容 **690,465 B（约 0.66 MiB）**、最多 **16** 个 ZIP 条目、单条目最大压缩比 **10.11:1**。

基于上述小样本及“普通 DOCX 允许图片/表格/公式图片”的已冻结范围，建议实现前检查采用以下候选值：原文件 **50 MiB**、解压总量 **250 MiB**、ZIP 条目数 **10,000**、单条目压缩比 **100:1**。它们分别约为现有观测最大值的 88 倍、379 倍、625 倍和 9.9 倍，目的是预留正常图文试卷余量，同时限制压缩炸弹风险。

在任何代码或部署配置写入这些数字前，WDV1-002 必须完成 `IMPLEMENTATION_PRECHECK`：对获准的脱敏 fixture/POC 样本重复统计这四项指标，记录只含汇总数值的结果，确认建议值仍有合理余量，并把最终选择写入 API 合同、配置说明和测试。若安全可用的样本不足以完成该检查，则阈值保持 `IMPLEMENTATION_PRECHECK`，不得声称已获产品负责人批准或凭空固定数字。

## 6. 身份、可见性与接口边界

G-07 只允许受控内部环境使用。开发和自动化测试可使用现有临时 `X-Actor-Id` 适配器；它只提供用于 `created_by` 和安全审计的 actor ID，不能被描述为正式登录、角色授权或 RBAC。

真实来源文件只能存在于受控内部环境。标注员通过受控应用/API 操作来源文件；私有文件存储本身仅向后端服务以及必要的受控运维人员开放，不向普通标注员提供直接存储访问能力。若无法证明该受控部署边界，实施仅可使用脱敏 fixture，不能接收真实试卷。

接口设计应遵循既有 `/api/v1`、请求 ID 与统一 `ApiError` 形状，但本合同只冻结以下行为，不冻结 URL 或 multipart 字段名：

- 成功响应只返回来源身份、版本号、元数据、哈希、状态和时间；不返回 `storage_uri`、文件字节或可下载地址。
- 缺失/无效的既有 actor 上下文可沿用 `401 UNAUTHENTICATED`；部署网关若拒绝访问可自行返回 `403 FORBIDDEN`。这两种结果都不要求 WDV1-002 新建用户、角色、权限策略或应用内 RBAC。
- 格式、容器、宏/嵌入内容和元数据错误返回 `422 VALIDATION_ERROR`，并仅指出安全的字段/规则类别。
- 超过请求或包安全阈值返回 `413 REQUEST_TOO_LARGE`。
- 幂等键冲突返回 `409 IDEMPOTENCY_CONFLICT`；相同哈希的非幂等重传采用后续 API 合同选定的最小 duplicate 语义，而不是由本合同预设 HTTP 状态。
- 私有存储不可用或提交前完整性校验失败返回 `503 SOURCE_STORAGE_UNAVAILABLE`；不得泄露路径、供应商响应或文件内容。

错误、访问日志、审计详情和 GitHub 评论只能记录 ID、请求 ID、错误代码、状态、大小类别和耗时，绝不记录正文、答案、文件字节、存储凭证、公开 URL 或完整私有路径。

## 7. 验收合同（G-07）

G-07 通过前，以下每项必须在 PostgreSQL 16 的一次性 `_test` 数据库及私有测试存储中实际验证：

1. 脱敏、有效 DOCX 可创建新 `Paper` 和版本 `1`，其元数据、SHA-256、创建者、时间和 `finalized` 状态正确。
2. 对已有 `Paper` 上传改变后的 DOCX 会创建下一个版本号；旧版本的所有元数据和存储字节保持不变。
3. 成功版本对应的私有存储对象哈希与数据库 `file_hash` 相同，且常规响应中不存在 `storage_uri`、绝对本地路径或下载 URL。
4. `.doc`、`.docm`、PDF、伪装扩展名、损坏 ZIP、宏/ActiveX/OLE、危险外部嵌入、超出 `IMPLEMENTATION_PRECHECK` 最终阈值的包和缺失必需 DOCX 部件均被拒绝；拒绝时不留下 `PaperVersion`。带普通外部 hyperlink 的 DOCX 被接收，且接收过程无网络访问。
5. 含代表性图片、表格、公式图片、分页、长文本和多段落的**脱敏有效 DOCX**可被完整保留；本项不读取、断言或输出其正文。
6. 同一幂等键的相同重放不创建重复记录；同一键不同载荷冲突；同一 `Paper` 的相同哈希使用新键重传时不创建新版本，并按后续 API 合同固定的 duplicate 语义返回结果。
7. 模拟存储失败、哈希不一致和数据库提交失败时没有 `finalized` 版本或成功响应；已 `finalized` 历史版本不受影响。
8. 常规业务外键仍为 `ON DELETE RESTRICT`；G-07 不增加物理删除接口或级联删除。
9. 自动化 fixture、日志、失败断言、截图和 GitHub issue/评论均不包含真实试卷、答案、凭证或私有解析输出。
10. 既有 Shenlun G-04/G-05 的迁移、服务和 API 契约测试仍通过；G-07 不改变现有题目保存、切换、冲突或提交流程。

通过证据应包含实际命令、测试数量/结果、PostgreSQL 16 版本、使用的一次性 `_test` 数据库、存储隔离方式、已知限制与 GitHub issue 记录。不得以 SQLite、公开对象链接、手工数据库插入或真实试卷代替验证。

## 8. 实施顺序与停止条件

获批后，WDV1-002 可按以下顺序开展：

1. 在 API 仓库创建独立 GitHub issue，记录本合同、开始时间、关键设计检查、阻塞和验证结论。
2. 先实现并测试私有存储适配边界、DOCX 安全校验、哈希与幂等；再接线来源版本定稿事务与安全响应。
3. 用一次性 PostgreSQL 16 和脱敏 DOCX fixture 完成 G-07 验收；关闭 issue 前记录实际结果和限制。
4. 仅在 G-07 通过后，才将来源结构化/解析工作带入 WDV1-003 / G-08。

出现下列任一情况必须停止，不得以临时绕过推进：

- 需要读取、解析、预览或分类内容才能让接收流程“可用”；
- 需要向普通用户公开原件或私有存储地址；
- 需要把 `X-Actor-Id` 当成生产认证/RBAC；
- 需要修改 G-06 冻结的 DOCX 范围、不可变性或人工优先规则；
- 发现现有表字段或 API 错误契约不足以表达上述结果，且需要新增 schema/API 语义。

最后一种情况应先补充本合同及相邻数据模型/API 文档，再经评审批准后实施；不得在代码中自行决定。
