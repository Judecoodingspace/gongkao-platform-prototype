# WDV1 G-08 Decision Review

**状态：待产品负责人逐项决定；非实施授权。** 本文只完成 `WDV1-003 / G-08` 的决策审查。它不批准迁移、解析器、LibreOffice、PyMuPDF、预览、API、React 或 `G-09` 实施。

**审查基线：** API `main` 的 G-07 接收实现 `9f26c0b` 与阶段治理同步 `8fbe0a6`；平台 `main` 的 G-07 验收记录 `03ac1cd`。原始 DOCX 接收已通过 G-07；G-08 只讨论如何在不改变原件的前提下，形成诚实的来源结构与预览证据。

## 已冻结、不是本轮 Decision 的规则

- 原始 DOCX 和已 `finalized` 的 `PaperVersion` 是不可变来源证据；后续处理不得覆盖或删除它们。
- 解析器只可产生来源结构：文字、图片或其他可靠来源块、顺序、可用页码/位置、告警及处理状态；不得推断题干、答案、材料、知识点、题型或任何业务角色。
- 正式题目仍是现有四个纯文本字段；图像、公式和表格目前仅能作为来源证据。
- 人工选择来源块、明确填入字段及字段到块的来源关系属于 G-09，当前不得实施。
- 上传失败与后续处理失败是不同状态；重新处理必须保留历史，不得静默覆盖。
- 外部用户输入仍只接受安全 `.docx`；内部 DOCX → LibreOffice → PDF 的派生路线不等于支持 PDF 上传。

### Decision 1 — 视觉阅读与可追溯来源块是否采用双层表示

#### 1. 这件事实际在决定什么

这决定标注员以后看原件时，是只得到一份“尽量像 Word 的阅读画面”，还是同时得到一组稳定、可以说明每段内容从哪里来的来源块。前者适合核对版式、图片和上下文；后者适合稳定地引用和追溯文字。两者可以来自同一份 DOCX，但服务的不是同一个目的。

#### 2. 为什么现在必须决定

若把视觉画面直接当成可复制、可追溯的唯一来源，PDF 复制常见的断行、分段问题会增加人工整理成本；若只保留抽取的文字块，图片、公式与排版关系又难以核对。后续把二者混为一层，会让“看起来正确”和“可稳定引用”互相牵制。

#### 3. 仓库 / POC 已知事实

- **已冻结事实：** G-06 允许结构块与可用页码/位置，但要求不得伪造坐标；G-08 需验收视觉预览、文字/图片来源证据和部分失败（`WDV1_G06_FROZEN_DECISIONS.md`）。
- **POC / 历史证据：** LibreOffice POC 的三份本地代表样本都可生成 PDF/HTML，人工检查认为 PDF/HTML 可与原 DOCX 版式对应；PDF 作为视觉候选保真较好，但直接复制文字会带入换行清理问题（`docs/libreoffice-poc.md`，尤其是“Preview and Copy Separation”）。
- **旧规划：** `spec.md`、`data-model.md` 提到连续页面预览可组合原子 `DocumentBlock`；它们不是已批准的生产实现。
- **尚未批准：** 生产中是否固定采用视觉层与来源结构层的双层表示，以及两层无法同时产生时如何对用户呈现。

#### 4. 2–3 个合理方案

1. 视觉层与来源结构层分开：视觉层用于核对原貌，来源块用于可选择、可追溯的证据。
2. 仅提供来源结构块，不承诺视觉层。
3. 仅提供视觉预览，并把用户的手工复制当作来源依据。

#### 5. 推荐方案

推荐方案 1。对标注员而言，既能看清图片、公式和布局，也不必把 PDF 的复制结果当作干净文本；对未来而言，两层可分别改进而不破坏来源链；对 V1 而言，它符合既有 POC 观察和 G-06 的“可靠结构、不伪造语义”原则。两层的对应关系只能保存已有的页码/位置，不能假装精确到无法证明的字符级映射。

#### 6. 产品负责人需要回答的问题

第一版是否确认同时保留两种用途：一边让人核对原 Word 的视觉样貌，另一边提供稳定的来源块？如果其中一边暂时失败，是否接受另一边仍然可用、同时明确提示缺失？

#### 7. 批准后解锁什么

解锁 WDV1-003 对来源结构层的最小边界设计，并为 WDV1-004 的视觉层验收边界提供前提；不会解锁预览 UI 或字段填入。

### Decision 2 — DocumentBlock 的自然切分粒度

#### 1. 这件事实际在决定什么

这决定系统把原文切成多大的“可追溯小段”。它不是决定哪段是题目或答案，而是决定标注员将来核对时，一段文字、一张图片或一个表格应当以多细的原始结构存在。

#### 2. 为什么现在必须决定

切得过碎，标注员要反复选择大量零散句子；切得过大，一段里混入太多无关内容，来源证明失去意义。若以“像题干”或“像答案”为理由切分，又会越过已经冻结的无业务语义边界。

#### 3. 仓库 / POC 已知事实

- **已冻结事实：** `DocumentBlock` 只能表达可靠来源结构，需保留阅读顺序和可用页码/边框；不得编码题目、答案等业务角色（`data-model.md`）。
- **POC / 历史证据：** PDF POC 使用 PDF 自然文字块与图像块，取得页码和 bbox（页面位置框）；多行自然段会作为同一文字块出现（`scripts/document_block_poc/build_document_blocks.py`）。
- **POC 局限：** PDF 文字抽取顺序在复杂表格/版式上可能不等同于原 Word，需要人工对照（`REVIEW_LOG.md`，`REV-20260803-01`）。
- **尚未批准：** 长段落的切分政策、表格是否作为独立块、以及 V1 何时保留未知/其他可靠块。

#### 4. 2–3 个合理方案

1. 以解析器可证明的自然结构为准：段落/自然文字块、图片、表格或其他可靠块；长段落保持完整，除非存在可证明的内部结构边界。
2. 统一按固定字数或句号切成小块。
3. 为了让块接近题目组成，按题号、作答要求等模式切分。

#### 5. 推荐方案

推荐方案 1。对标注员而言，一块通常仍保留可读上下文，长段不会因技术规则被拆得支离破碎；对未来而言，可以在不改变原始块含义的情况下做展示组合；对 V1 而言，它不把解析器变成题目理解器。若一段过长但没有可靠内部边界，应保留整段并让后续人工选择多个块，而不是猜测业务边界。

#### 6. 产品负责人需要回答的问题

是否同意第一版按文档本身可证明的段落、自然文字区域、图片、表格等来切块，而不为了“更像一道题”人为切分？遇到很长但结构上完整的一段，是否宁可保持一整块？

#### 7. 批准后解锁什么

解锁 WDV1-003 的最小结构块定义、顺序断言和脱敏 fixture 验收；不会解锁业务标签或自动拆题。

### Decision 3 — 重新结构化的历史与当前结果

#### 1. 这件事实际在决定什么

这决定同一份已经保存的 Word 被再次处理后，工作人员还能不能知道上一次系统给出了什么结构。例如第一次得到 120 块、后来工具改进后得到 123 块：两次都是对同一原件的不同处理结果，而不是把历史悄悄改写掉。

#### 2. 为什么现在必须决定

不先确定这一点，工具升级或人工重试可能覆盖旧结构。将来已有人工来源关系时，人会突然发现原先引用的块不见了，却无法解释为什么；也无法复核处理器版本变更带来的差异。

#### 3. 仓库 / POC 已知事实

- **已冻结事实：** G-06 明确重新处理要产生独立 processing record/history，不能静默覆盖早先结果；处理失败不得把成功上传重标为上传失败（`WDV1_G06_FROZEN_DECISIONS.md`）。
- **已实现事实：** G-07 的 `PaperVersion` 已为不可变 DOCX 来源版本，不含任何来源块或处理历史（API `9f26c0b`，`WDV1_G07_ACCEPTANCE_REPORT.md`）。
- **旧规划：** `data-model.md` 提及 parser 版本、配置、创建时间等候选信息，但尚未批准为迁移设计。
- **尚未批准：** 是否允许多次结果、如何标示当前可用结果、旧结果保留多久、以及未来人工关联如何与特定结果保持对应。

#### 4. 2–3 个合理方案

1. 每次人工发起的处理都形成独立、只读结果；同一原件可有一个明确标示的当前结果，旧结果保留供追溯。
2. 允许重新处理，但用新结果直接替换旧结构。
3. 同一原件只允许处理一次，工具变更也不能重跑。

#### 5. 推荐方案

推荐方案 1。对用户而言，能看到当前建议来自哪一次处理，也能在异常时回看旧结果；对未来而言，工具升级不会破坏已经建立的来源证明；对 V1 而言，手动重处理足够，不需要复杂自动重试。未来如果某个旧块已被人工引用，该引用必须留在产生它的那次结果上，不能因新结果自动失效或重指向。

#### 6. 产品负责人需要回答的问题

当同一份 Word 因工具升级或人工重试而得到不同的结构结果时，是否同意两次结果都保留，只明确其中哪一次是当前建议使用的版本？已经被人工使用过的旧来源块，是否必须始终可追溯回原来的处理结果？

#### 7. 批准后解锁什么

解锁 WDV1-003 对处理历史、当前结果和不可覆盖关系的实施合同设计；不会在本审查中定义完整表结构。

### Decision 4 — WDV1-003 是否先交付文字来源块基础

#### 1. 这件事实际在决定什么

这决定团队是否先把“原文能够被稳定地按顺序读出并留下来源位置”做好，再在后续切片完成图片证据和视觉预览。它不是降低 G-08 的最终要求，而是把工作拆成可验证的小步。

#### 2. 为什么现在必须决定

若一次同时处理文字、图片、视觉预览和各种部分失败，出现问题时很难判断是转换、抽取还是展示出了错。反过来，若文字先行却被误称为整个 G-08 完成，会掩盖图片、公式和视觉核对仍未解决的事实。

#### 3. 仓库 / POC 已知事实

- **已冻结事实：** G-08 最终必须验证视觉预览、文字/图片来源证据及部分失败行为（`WDV1_G06_FROZEN_DECISIONS.md`）。
- **POC / 历史证据：** LibreOffice → PDF → PyMuPDF POC 可以给文字块提供顺序、页码和 bbox，也能尝试提取图片；但这只是 POC，尚未验证生产 worker、安全隔离或跨样本稳定性（`REV-20260803-01`）。
- **尚未批准：** `WDV1-003` 是否可先以 ordered text blocks、可靠页码/位置和处理状态为范围，及其与 G-08 的关系。

#### 4. 2–3 个合理方案

1. WDV1-003 先完成文字来源块、顺序、可用位置和处理状态；WDV1-004 再完成视觉预览、图像证据及可见的部分失败体验。
2. WDV1-003 必须同时完成文字、图片、预览和部分失败。
3. 先只做视觉预览，结构块延后。

#### 5. 推荐方案

推荐方案 1。对用户而言，第一步已能建立可审计的文字来源基础，但不会误以为图片或预览已可靠；对未来而言，视觉渲染和图像证据可独立加强；对当前 V1 而言，符合“先证实可靠结构，再验证完整阅读体验”的风险控制。必须明确：`WDV1-003 = COMPLETE` 不等于 `G-08 = PASS`。

#### 6. 产品负责人需要回答的问题

是否同意把 G-08 拆成两步：先验证稳定的文字来源块，再验证视觉预览、图片证据和部分失败的用户体验？是否同意第一步完成时只称为 WDV1-003 完成，而不宣布 G-08 通过？

#### 7. 批准后解锁什么

解锁只覆盖文字来源结构基础的 WDV1-003 实施合同草案；图片、视觉预览和 G-08 PASS 仍留在 WDV1-004。

### Decision 5 — 第一版生产候选的结构化处理路线

#### 1. 这件事实际在决定什么

这决定系统第一版用哪条工具路线把已经安全保存的 DOCX 变成“按页、按顺序、可标明位置”的来源结构。这里的“生产候选”意思是值得进入受控实现验证的路线，不等于已经保证对所有 Word 文件都正确。

#### 2. 为什么现在必须决定

不同路线的保真度、可维护性和运行风险不同。若在实现中临时选择，可能把本机偶然跑通的 POC 当成长期承诺，也可能在工具不可用时无边界地改用会损失公式图片或位置的信息。

#### 3. 仓库 / POC 已知事实

- **POC 已证明：** LibreOffice 已在本机把三份代表 DOCX 转为 PDF；人工对照显示当前样本的 PDF/HTML 与 Word 版式对应（`docs/libreoffice-poc.md`）。
- **POC 已证明：** 从 LibreOffice PDF 读取时，PyMuPDF POC 能产生文字/图片块，以及页面号和 bbox；对于公式图片，PDF 路线在观察样本中保留了 Docling 曾输出为 24×11 占位图的内容（`scripts/document_block_poc/build_document_blocks.py`、`REV-20260803-01`）。
- **POC 阻塞：** Docling 1.10.0 在本机 Windows/Python 3.13 环境因 `torch` 的 `c10.dll` 加载失败，无法 import；其 DrawingML 路线未能重新验证（`docs/docling-poc.md`）。
- **仍只是候选：** LibreOffice → PDF → PyMuPDF 尚未经过生产 worker 隔离、超时、安全执行、跨样本稳定性、复杂表格读取顺序或 API/数据库集成验证。

#### 4. 2–3 个合理方案

1. 将 LibreOffice → PDF → PyMuPDF 作为 WDV1-003 的受控生产候选，先只产出文字来源结构；保留可替换的解析器适配边界。
2. 先修复并采用 Docling 作为唯一主路线，再开始 WDV1-003。
3. 暂不选路线，继续只做 POC，推迟 G-08。

#### 5. 推荐方案

推荐方案 1。对用户而言，优先走当前已能保留视觉布局和公式图片、并能给出页码/位置的路线；对未来而言，解析器适配边界允许在 Docling 环境稳定后比较或替换，不会锁死数据模型；对当前 V1 而言，不需要先解决与产品目标无直接关系的 torch 环境问题。批准的是“受控验证候选”，不是对所有 DOCX 的无条件承诺。

#### 6. 产品负责人需要回答的问题

是否同意先用“DOCX 转为内部 PDF，再从 PDF 取得文字位置”的路线做受控验证，同时保留未来可替换工具的边界？如果遇到复杂表格或版式导致文字顺序不可靠，是否同意诚实标为部分处理或失败，而不是猜测顺序？

#### 7. 批准后解锁什么

解锁 WDV1-003 实施合同对候选处理器、适配边界、环境隔离和失败验证的约束；不会批准 PDF 上传、视觉预览或生产部署。

### Decision 6 — 部分结构化的最低诚实语义

#### 1. 这件事实际在决定什么

这决定系统读懂大部分 Word、但某一页或某个区域不能可靠整理时，怎样既让人继续使用已经可靠的内容，又不把不完整结果装作完整。

#### 2. 为什么现在必须决定

若只有“成功/失败”两种结果，团队容易把可用部分全部丢弃，或相反地掩盖坏区域。没有统一表达方式，标注员无法判断哪些内容可用、哪些仍需打开原件或手工处理。

#### 3. 仓库 / POC 已知事实

- **已冻结事实：** G-06 已规定 partial structuring：展示可靠块、明确标出不可靠区域，且不得把部分成功呈现为完整；文档与预览仍可保留（`WDV1_G06_FROZEN_DECISIONS.md`）。
- **POC / 历史证据：** PDF 文字抽取在复杂表格、复杂版式上的阅读顺序可能不可靠；图片抽取也可能失败（`REV-20260803-01`、`build_document_blocks.py` 中的 best-effort 图像处理）。
- **尚未批准：** 什么信息必须面向用户可见、何时使用 `partial`、是否需要页级/区域级占位提示，以及整体 `failed` 的最低门槛。

#### 4. 2–3 个合理方案

1. 允许 `success`、`partial`、`failed`：partial 保留已验证的块，并给出至少页级或区域级的可理解告警；无法建立任何可靠结构时为 failed。
2. 只要存在一处不可靠就整体 failed。
3. 只要能产生一些块就一律 success，并把问题放在日志中。

#### 5. 推荐方案

推荐方案 1。对用户而言，可继续查看和使用可靠部分，同时清楚知道应回到原件核对的位置；对未来而言，失败信息能积累为改进工具的证据；对 V1 而言，状态足够清晰，不需要难以解释的复杂置信度分数。最低可见信息应包含处理并非完整、受影响的页码或可定位区域（仅在可靠时）、以及“原始 Word 未受影响”的说明。若没有任何可靠块、原件无法安全读取，或无法诚实定位不可靠范围，应整体 failed。

#### 6. 产品负责人需要回答的问题

是否同意系统在“多数内容可靠、少数区域不可靠”时显示“部分完成”，保留可靠部分，并明确指出受影响的页或区域？什么程度的不完整会让你宁可整个结果都不提供？

#### 7. 批准后解锁什么

解锁 WDV1-003 对 success / partial / failed 的最小产品含义和验收场景；不会解锁 UI、自动重试或复杂置信度系统。
